# Boss Daddy v2 — Full Codebase Audit (2026-08-16)

Method, in three passes.

**Pass 1 — fan-out.** Nine static dimensions (RLS, authz, injection, data-layer, rendering-perf, cache-correctness, observability, type-safety, dead-code) plus four targeted gap investigations (account deletion & data retention; Stripe→Printful fulfilment chain; email consent & deliverability; local-day boundary across goals and savings). Every candidate faced an adversarial refuter that defaulted to rejecting: 60 confirmed, 44 refuted. Four confirmed entries are duplicates of the same defect reached from different dimensions, so the distinct count for this pass is ~56.

**Pass 2 — recovered dimension.** A tenth dimension (test coverage vs. risk; dependency currency; guard/CI conformance) crashed mid-run and was re-executed separately. It **self-refuted rather than facing an independent refuter**, so findings #61–#71 carry marginally lower verification confidence than #1–#60. It contributed four Highs, including the highest-consequence defect in this report (#61). One item the pass-1 appendix had refuted — money-path test coverage — was **re-instated as #65**, because the re-run produced the specific evidence (`adminResult` never reset to null) that the original refutation lacked.

**Pass 3 — cross-model review.** A second model reviewed the report with full context and re-verified the five pass-1 Highs against source. All five held. The review also (a) caught that finding #2's originally recommended fix would have **introduced an authentication bypass** — see #2's Fix note; (b) escalated #61; and (c) forced a live check of repository protection that surfaced #63. One review escalation was itself refuted on verification (see Appendix, `review-pass`).

Totals across all three passes: **76 confirmed, 45 refuted.**

Verdict: **7 / 10.** No critical survived verification and nothing is remotely exploitable by an unauthenticated stranger for cross-user *read* of private data — the RLS doctrine in `CLAUDE.md` is doing real work, and 44 refutations (many killed by an in-file comment that already documented the tradeoff) show the codebase is unusually well-reasoned for its size. Points come off for four structural weaknesses: the money path (Stripe→Printful) has no reconciliation and swallows write errors; erasure is incomplete (Storage, newsletter, audit trail); day-boundary arithmetic is still split between UTC and browser-local; and every recurring defect class was fixed at the instance, never gated, so the same shape keeps reappearing in new files.

**Amended after passes 2 and 3.** The score stays at 7/10, but the fourth weakness is worse than pass 1 could see. It is not merely that fixes weren't gated — **the gate layer itself is not wired up.** Seven of the eight `check:*` guards never run before code reaches master (#62); the pgTAP suite that exists to catch exactly the #1 class asserts 6 tables out of ~28 and passed 16/16 while #1 shipped (#64); and the branch protection configured in July has drifted to zero required status checks (#63). Every "add a guard" recommendation in the remediation plan below is inert until #62 and #63 are fixed, which is why they are now Phase 0. Separately, #61 puts a legally-required gate — one `CLAUDE.md` marks as non-bypassable — on a code path with no check. It is not Critical (it needs an authenticated author/admin action, and there is no cross-user or unauthenticated exploit) but it is first in remediation order.

## Critical and high findings

### 1. Migration 106 reverts migration 080's savings DELETE fix

| | |
|---|---|
| Location | `supabase/migrations/106_savings_admin_scope_moderation_only.sql:114` |
| Effort | S |
| Dimension | rls |

**Evidence.** `080_savings_entries_delete_policy.sql:1-17` documents the bug it fixes: the `for all` policy's `with check` is not applied to DELETE, so a contributor removed from `savings_goal_participants` could still delete their historical rows. 080 drops `savings_entries self_write` (`:17`) and replaces it with per-operation `self_insert` (`:20`), `self_update` (`:34`), `self_delete` (`:54`), each requiring `is_savings_goal_participant(goal_id)`. `106:114-124` re-creates `self_write` as `for all ... using (contributor_id = auth.uid())`. Permissive policies OR, so the effective DELETE predicate collapses back to `contributor_id = auth.uid()`. Nothing after 106 touches these policies. Separately, 106's stated purpose was to strip `is_admin()` from savings writes; it never touched 080's three policies, which still carry `or is_admin()` (`080:28,42,49,62`).

**Failure scenario.** Alice removes ex-partner Bob from a shared goal's participants. Bob, still signed in, issues `DELETE /rest/v1/savings_entries?contributor_id=eq.<bob>&goal_id=eq.<goal>` with the public anon key. All 40 of his historical contribution rows are wiped from the shared goal — precisely what 080 was written to prevent. Second: the admin's ordinary session client can write any user's savings entries via the surviving `or is_admin()` clauses.

**Fix.** Drop `savings_entries self_write` and do not recreate it; drop/recreate 080's three per-operation policies without `or is_admin()`. Add a check asserting `savings_entries` has no `FOR ALL` policy.

### 2. `profiles` is anon-readable and now carries moderation columns

| | |
|---|---|
| Location | `supabase/migrations/043_profiles_public_read.sql:22` |
| Effort | M |
| Dimension | rls |

**Evidence.** `043:21-25` creates `profiles_public_read ... to anon, authenticated using (true)`, justified column-wise ("only public-facing identity data"). That was true at 043. Since then: `050_account_moderation.sql:11-19` added `account_status`, `suspended_until`, `moderation_reason`, `moderation_note`, `moderation_action_at`, `moderation_action_by`, `deletion_requested_at`; `085:14` added `email_new_message`; `124:18` added `trust_locked`; `140:113-117` added `connection_requests_from`, `discoverable_by_email`. No column-level GRANT exists on `profiles` in any of the 146 migrations, so anon retains SELECT on every column. `app/api/admin/users/moderate/route.ts:31` accepts a 2000-char free-text `note`; `:62-63` writes it to `moderation_reason` / `moderation_note`. (No email column exists on `profiles` — `lib/supabase/database.types.ts:2684-2705` — so no addresses leak.)

**Failure scenario.** Anyone lifts `NEXT_PUBLIC_SUPABASE_ANON_KEY` from the client bundle and issues `GET /rest/v1/profiles?select=id,username,account_status,moderation_reason,moderation_note,deletion_requested_at` with no session, receiving the internal admin note written about every member, their suspension reason, and whether they requested deletion.

**Fix — split the table. Do NOT use the column-GRANT approach.**

Move `account_status`, `suspended_until`, `moderation_reason`, `moderation_note`, `moderation_action_at`, `moderation_action_by`, `deletion_requested_at` into a `profile_moderation` table with an admin-only policy, plus a self-read policy for the columns a member legitimately needs about themselves. Keep the notification/discovery preference columns on `profiles` behind a `user_id = auth.uid()` self-read policy.

⚠️ **The originally recommended fix was withdrawn in pass 3 because it introduces an authentication bypass.** It read: `revoke select on profiles from anon, authenticated;` then `grant select (id, username, role, display_name, tagline, bio, avatar_url, created_at)`. Column privileges *are* checked before RLS and PostgREST *does* honour them — the mechanism is correct. The problem is the blast radius. `lib/proxy/moderation.ts:21-27` reads `account_status, suspended_until` **with the user's own session client, on every authenticated request**, and line 27 is `if (!profile) return null`. Under that GRANT the query returns `42501 insufficient_privilege`, supabase-js yields `{ data: null }`, and the moderation gate **fails open — banned and suspended users pass straight through.** The same denial breaks every self-read of `email_new_message`, `discoverable_by_email` and `trust_locked`. A hardening patch that silently disables the ban system is strictly worse than the leak it fixes, and its failure mode is invisible in exactly the way five other findings in this report are invisible. If the GRANT route is ever revisited, `lib/proxy/moderation.ts` must move to the admin client *first*, in the same migration.

### 3. Hard account delete never touches Storage — and kid photos are in a public bucket (bundles #23)

> **Read #3 and #23 as one defect.** Separately they under-read as High + Medium. Together the story is: a member uploads a photo of his child; the file lands in a bucket created `public = true` with `FOR SELECT USING (bucket_id = 'avatars')`, so it is anonymously readable and path-enumerable from the moment of upload (#23); he later requests deletion; the cron deletes the row that holds the only reference to the path, emails him that all associated data was permanently removed, and **leaves the child's photo publicly served forever** (#3). Fix them in one sitting: the pre-delete storage sweep below, plus moving `kids/` behind the private-bucket + owner-gated signed-URL proxy already proven by `dm-media`.

| | |
|---|---|
| Location | `app/api/cron/delete-expired-accounts/route.ts:64` |
| Effort | M |
| Dimension | gap: account deletion & retention |

**Evidence.** The cron's entire erasure is `admin.auth.admin.deleteUser(target.id)` plus FK cascade; there is no `admin.storage` call in the file. Objects live at `{user_id}/avatar.webp` (`app/api/profile/avatar/route.ts:56-60`) and `kids/{kidId}/avatar.webp` (`app/api/kids/[id]/photo/route.ts:81-85`) in the `avatars` bucket, created `public = true` (`061:13-24`) with `FOR SELECT USING (bucket_id = 'avatars')` (`061:33-35`). `kid_profiles.user_id` cascades from `profiles` (`076:22`), which cascades from `auth.users` (`001:7`), so the DB deletes the rows without ever running the app-level cleanup in `lib/dad-tools/kid-actions.ts:256`. Same gap covers `dm-media` paths held in `messages.attachment_path` (see low finding).

**Failure scenario.** A member uploads a photo of his 4-year-old, then requests deletion. 30 days later the cron deletes him; `kid_profiles.photo_url` — the only record of the path — is destroyed with the row. The WebP is still served anonymously at `/storage/v1/object/public/avatars/kids/<kidId>/avatar.webp` indefinitely, now unreferenced and unreclaimable, while the user receives an email saying all associated data was permanently removed (`emails/AccountStatusEmail.tsx:76`).

**Fix.** One pre-`deleteUser` storage sweep driven off rows that still exist at that point: list/remove `avatars/{user_id}`, `avatars/kids/{kid_id}` for each of the user's `kid_profiles`, and `dm-media` paths from `messages.attachment_path where sender_id = target.id`. Log per-user failures rather than aborting the batch.

### 4. Printful recipient has no `address2` — every apartment order ships without the unit

| | |
|---|---|
| Location | `lib/printful.ts:65` |
| Effort | S |
| Dimension | gap: Stripe→Printful fulfilment |

**Evidence.** `PrintfulOrderRecipient` (`lib/printful.ts:65-73`) declares seven fields with no `address2` and no index signature. The single `createOrder` call site builds its recipient at `app/api/webhooks/stripe/route.ts:248-256` with only `address1: sd.address.line1`. `line2` *is* captured (`:170`), persisted to `orders.shipping_address` (`:197`), rendered on the confirmation page (`app/(public)/order/[id]/page.tsx:137`) and in the email (`emails/OrderConfirmationEmail.tsx:147`). Stripe collects it via `shipping_address_collection` (`app/api/checkout/route.ts:53`). Printful's v1 recipient object supports `address2`.

**Failure scenario.** "1420 Chestnut St, Apt 7C" — the buyer sees "Apt 7C" on the order page and in the email, so it looks captured. Printful receives street only. Carrier delivers to a 40-unit building with no unit number: lobby drop or return to sender. Invisible internally, because every stored and rendered copy is correct — only the copy Printful got is wrong.

**Fix.** Add `address2?: string` to the interface; pass `address2: sd.address.line2 ?? undefined`. Add a webhook test asserting the `createOrder` payload round-trips `line2`.

### 5. Savings streak reads 0 every evening west of UTC

| | |
|---|---|
| Location | `lib/dad-tools/savings.ts:324` |
| Effort | M |
| Dimension | gap: local-day boundary |

**Evidence.** Writes are browser-local: `ContributionButton.tsx:80` uses `todayYMDLocal()` with a comment explaining that server-UTC would stamp late-evening contributions with tomorrow's date, feeding `contributedOn` at `:170`. Reads are server-clock: `computeStats(goal, entries)` is called with no `asOf` at `savings-actions.ts:381`, `:414` and `app/(tools)/tools/family/[id]/page.tsx:341`, so `asOf = new Date()` (`savings.ts:451`). `walkStreakAndBank` derives `todayKey = todayUnitKey(cadence, asOf)` (`:324`) via `dateToYMD` (`:136`), which reads `getFullYear/getMonth/getDate` — UTC on Vercel. Any non-current uncovered unit sets `streak = 0` (`:334-339`).

**Failure scenario.** Pacific dad, daily $5 goal, logs every evening. At 7:30pm PT on 08-15 (= 02:30Z 08-16) he opens the goal before logging. `todayKey = '2026-08-16'`, so unit `'2026-08-15'` is uncovered and not current → `streak = 0`. `ProgressBlock.tsx:57-60` and `GoalCard.tsx:86-90` render "0 days" on a 14-day run. The same call makes `expectedTotalAsOf` count 15 days ($75) against $70 saved, so `buildCatchUpSuggestion` renders a CatchUpPanel telling him to double up (`app/(tools)/tools/savings/[id]/page.tsx:176`). Window is 17:00–24:00 PT daily.

**Fix.** Store the goal owner's IANA zone (reuse the goals-spine per-row timezone pattern) and compute `asOf`'s day key with `localDateInZone(now, zone)`. Minimum viable: thread a browser-supplied `todayYMD` into the page's `computeStats` call exactly as `ContributionButton` already threads it into the write.

### 61. The affiliate disclosure gate is bypassable via the scheduling path

| | |
|---|---|
| Location | `app/api/cron/publish-scheduled/route.ts:44-50,71` |
| Effort | S |
| Dimension | tests-deps (pass 2), escalated and corrected in pass 3 |

**Evidence.** The FTC disclosure gate exists in exactly two places: `app/api/reviews/route.ts:48` (create) and `app/api/reviews/[id]/submit/route.ts:36` (submit). `supabase/migrations/001_initial.sql:47` declares `disclosure_acknowledged` with `DEFAULT FALSE` and no CHECK or trigger, so the database enforces nothing. `publish-scheduled` selects reviews and guides on `.not('scheduled_publish_at','is',null).lte('scheduled_publish_at', now).in('status',['draft','pending','rejected'])` and writes `status: 'approved'` at `:71` — the string "disclosure" does not appear in the file. `scheduled_publish_at` is accepted on the ordinary edit path (`app/api/reviews/[id]/route.ts:217`), which authors may use on their own drafts. **Setting a publish date therefore routes around `submit` entirely.**

Separately, the admin moderation branch (`app/api/reviews/[id]/route.ts:80-82`) writes `status = 'approved'` without reading the row's current status or re-checking the gate. Zero tests reference any review route.

**Failure scenario.** A review containing `[[BUY:]]` affiliate tokens sits in `draft` with `disclosure_acknowledged = false`. The author sets a publish date — an ordinary editorial action, not an attack. Within 15 minutes the cron publishes it to a public, indexed URL with affiliate links and no disclosure. `CLAUDE.md` marks this gate as a legal compliance requirement that must not be bypassed. Follow-up reviews are the most exposed class, because `app/api/reviews/[id]/schedule-followup/route.ts:258-259` creates them with `disclosure_acknowledged: false` by construction while computing `has_affiliate_links` from AI-drafted content.

**Refuted sub-claim (pass 3).** The pass-3 review initially asserted a zero-touch chain: that `schedule-followup` itself sets a publish date, making the cron publish undisclosed content unattended. **This is false.** The insert at `schedule-followup/route.ts:258-264` sets `status`, `parent_review_id`, `milestone_label` and `milestone_days` but **never sets `scheduled_publish_at`**, and the cron requires it non-null. The draft sits inert until a human schedules it. The defect is real; the automated mechanism is not.

**Also.** The cron transitions `draft → approved` directly, which is outside the state machine documented in `CLAUDE.md` (`pending → approved`, admin only). Either the doctrine needs a documented cron exception or the cron needs to require `pending`.

**Fix.** Add `has_affiliate_links && !disclosure_acknowledged` to the cron's filter — skip those rows and `Sentry.captureException` so they surface rather than silently never publishing. Re-check the gate and assert `current.status === 'pending'` on the API approve branch. Add a route-level test table covering every legal and illegal transition.

### 62. Seven of the eight prebuild guards never run before code reaches master

| | |
|---|---|
| Location | `.github/workflows/ci.yml:20-22`, `package.json:9` |
| Effort | S |
| Dimension | tests-deps (pass 2) |

**Evidence.** `ci.yml` runs `npm ci`, `npm run check`, `npm test`. `npm run check` is `tsc --noEmit && eslint`. All eight `check:*` guards live in the `prebuild` script, which fires only under `npm run build` — i.e. on Vercel, after merge. `.git/hooks/pre-commit` runs `check-middleware-convention.mjs` alone and lives in `.git/`, so it exists on one machine and reaches no clone or runner. `ci.yml`'s own header comment documents this exact lesson, having learned it for `tsc`/`eslint` only.

**Failure scenario.** A commit adding `className="text-xs text-faint"` passes `tsc`, passes `eslint` (`eslint.config.mjs:69-82` restricts only raw `orange-N` / `neutral|gray-N`), goes green in CI, and then fails `check-color-roles.mjs` during the Vercel production build. Master is undeployable and the signal arrives after the fact. The same holds for OG coverage, JSX spaces, storage upload bodies, prose-invert, invisible shadows and goals-identity language.

**Fix.** Add `- run: npm run prebuild` to `ci.yml`. Note this is only a gate once #63 is fixed.

### 63. Branch protection has drifted — there are zero required status checks

| | |
|---|---|
| Location | GitHub repo settings, `mbrktdaddy/bossdaddy-v2`, branch `master` |
| Effort | S |
| Dimension | review pass (pass 3) |

**Evidence.** Live query of `repos/mbrktdaddy/bossdaddy-v2/branches/master/protection` returns `enforce_admins: true`, `required_status_checks: null`, and no required pull-request reviews. `git log --format='%h %p %s' -12` shows a fully linear history with no merge commits — every recent commit was pushed directly to master. ## Themes

**1. Fixes were applied to instances, never to classes — this is the dominant shape, and it is confirmed, not contradicted.** Six findings are literally a *later* file re-committing a bug an *earlier* file already fixed and documented:

- 106 re-created the exact `FOR ALL` policy 080 dropped (#1) — the migration whose stated job was hardening savings re-opened the hole.
- `lib/email.ts:3-7` exists specifically because "Resend does not throw on API errors"; three send sites still bypass it (#18, #32, #57).
- `lib/wishlist-emails.ts:60-81` gets notify-on-success right; `publish-scheduled` re-implements it wrong (#32, #51).
- `lib/goals/sweep.ts:1003-1015` carries a comment warning against `listUsers`; four other call sites use `listUsers` anyway (#30, #58).
- `lib/products.ts:140` ships a batch helper documented as "one round-trip"; three sibling pages in the same directory hand-roll the N-query loop (#43, #45).
- `lib/revalidate.ts` was written *because* "the guide routes all forgot the two category surfaces" — and the helper itself then forgot `/gear/category` and both tag surfaces (#14, #46, #49).

The single contradicting case is instructive: `lib/proxy/slug-redirect.ts:9-12` and `sentry-swallows-redirects` were refuted precisely *because* the tradeoff was written into the file and therefore survived. Comments preserved decisions; only executable guards preserved behaviour.

**2. The money path has no reconciliation loop.** Every write between Stripe and Printful is fire-and-forget: `order_items` insert (#17), `printful_order_id` writeback (#16/#27), refund status (#50), plus a `catch` whose comment promises an admin retry panel that does not exist (#26). Combined with the shipped-but-unreadable tracking data (#28) and the unvalidated cart→checkout hop (#29, #55), the whole chain is single-attempt with no sweeper. Two of the five webhook write sites are already known to have caused a production incident (migration 103's header). The missing artefact is not more error handling — it is one cron that queries `status='paid' AND printful_order_id IS NULL`.

**3. Erasure was implemented as "delete the auth row and let FKs do the rest," and FKs cover only part of the graph.** Storage has no FK (#3, #54), `newsletter_subscribers` has no `user_id` (#25, #33), and the one table that *does* have an FK — `moderation_actions` — cascades away the audit record the cron deliberately writes first (#24). Three of the four gaps are invisible from the DB schema alone, which is why they all shipped: the schema looks complete.

**4. Two clocks, three date idioms, no owner.** The already-known three-idiom split shows up as user-visible defects in every subsystem it touches: savings streak (#5), savings reminders (#34), savings start date (#60). Writes are browser-local by deliberate fix; reads are server-UTC by omission. The goals spine already solved this with a per-row IANA zone; savings never adopted it. This is one missing `localDateInZone(now, zone)` at four read sites, not four bugs.

**5. Silent-success is the house error-handling style.** Nine confirmed findings share one shape: an unchecked supabase-js or Resend return value followed by an unconditional success response (#16, #17, #18, #19, #21, #50, #51, #52, #57). Both libraries return errors rather than throwing, so `try/catch` reads as coverage while providing none. Zero Sentry calls exist in any of the 13 cron routes. This is the single highest-leverage lint target in the repo.

**6. The gate layer is itself ungated — added in pass 2/3, and it subsumes theme 1.** Theme 1 said fixes were applied to instances and never gated. Passes 2 and 3 found the sharper version: **where gates were built, they were not wired up.** Eight guard scripts exist and seven never run pre-merge (#62). A pgTAP suite exists to catch the #1 defect class and asserts 6 of ~28 tables, passing green while #1 shipped (#64). Branch protection was configured in July with a required status check and has since drifted to none (#63). A smoke test exists and has been failing on healthy deploys for long enough that nobody reads it (#66). Two hand-maintained parallel lists — `ADMIN_ONLY_PATHS` (#68) and `FAIL_CLOSED_TYPES` (#69) — are the enforcement mechanism for auth scope and AI spend, with no test asserting membership.

The pattern is not carelessness; every one of these artefacts was built deliberately and correctly. It is that **building the guard and arming the guard are separate acts, and only the first one feels like progress.** Any remediation that ends at "wrote the check" repeats it.

**7. Two verification failures, both structural, both worth designing around.** This audit's method produced two distinct classes of error worth recording:

- *Fan-out misses cross-cutting chains.* Finding #61 spans authz, cron correctness and legal compliance. Nine dimension agents each correctly saw nothing wrong in their own slice. The completeness critic that should have caught it was given finding **titles and coverage notes, not code**, and no reader of summaries can trace a defect through three files. Fix: give the critic file lists and read access.
- *A single reviewer with full context finds chains but over-claims.* Pass 3 found #61 and the #2 auth-bypass trap — neither reachable by fan-out — but also asserted a zero-touch cron mechanism that does not exist, and it went unchallenged because pass 3 had no refuter. Pass 1 killed 44 such claims; pass 3 had no equivalent.

Neither method dominates. The working combination is **fan-out for coverage, single-reviewer for chains, refutation over both** — and every escalation verified against source before it is believed, including the reviewer's own.

## Remediation plan

Ordered by risk removed per unit effort. One phase per sitting. Gates preferred over fixes: where a gate exists, ship the gate first — it fixes the class and prevents the next instance.

**Revised after passes 2 and 3.** Phase 0 is new and must come first: it arms the enforcement layer that every later phase's "Prevention" column depends on. Phase 1 has been re-ordered — #61 leads on legal exposure at S effort, and #2's remedy changed (see the finding).

### Phase 0 — Arm the gates ✅ DONE 2026-08-16, but NOT as originally written

**The original Phase 0 said "restore the required status check on `master`" and "add `prebuild` to `ci.yml`." That recommendation is WITHDRAWN.** The operator had deliberately removed the required check, and rejects the branch → Playwright → PR → merge pipeline as not worth the time, tokens, or friction for a solo developer iterating fast. Re-imposing it would have been the audit prescribing team process to a one-person team.

Measurement dissolved the tradeoff instead. The real cost was never the guards:

| | Before | After |
|---|---|---|
| `.git/hooks/pre-commit` | 1 guard + `tsc --noEmit` + `eslint` = **~121 s per commit** | **all 8 guards = 1.25 s** |
| `npm run check` | `tsc && eslint` = ~121 s | `tsc && eslint --cache` = **~7 s warm** |
| Guards actually running pre-commit | 1 of 8 | **8 of 8** |

The eight `check:*` guards cost **1.2 s combined**. They were suspended for speed while a 121-second `tsc`/`eslint` pair sat in the same hook — under 1% of the wait was the thing that got cut. Inverting the hook made commits ~100× faster *and* increased guard coverage eightfold, with no remote gate, no PR, and no waiting.

**Shipped:** pre-commit rewritten to the eight guards only (with a header explaining why `tsc`/`eslint` were removed, so nobody restores them) · `lint` and `check` now use `eslint --cache` · new `check:full` for a cache-free run when a dependency-level type change may have staled cached lint results · `.eslintcache` gitignored. `ci.yml` still runs on push as a **non-blocking** signal; nothing is required.

**Standing constraint for future remediation:** price every proposed safeguard in *seconds per commit*. Anything over a couple of seconds belongs in an occasional manual command, not an automatic gate. See `feedback_lightweight_process_no_pr_ceremony` in memory.
